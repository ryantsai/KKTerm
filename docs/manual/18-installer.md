## What it is

The **Install Helper Module** is a built-in Activity Rail destination that installs, updates, and uninstalls a curated catalog of Windows AI tool stacks — git, node, python, docker, AI coding CLIs, local AI platforms, and supporting utilities. It is grouped with the other built-in Module buttons near the top of the rail, with its own icon (`Package`).

The catalog **ships with the KKTerm release**: the JSON list of supported tools is compiled into the binary at build time. Updates to the catalog ride with each release. See `docs/ADR/0008-installer-helper-bundled-catalog.md` for the rationale and what it supersedes.

In portable mode, the persistent caption `installer.portableMachineLocalNotice` states the ownership boundary: Install Helper tools, managed web-app runtimes, databases, uploads, models, logs, and service definitions stay on the current machine. Managed apps continue to use `%LOCALAPPDATA%\KKTerm\installer\apps`; installed and portable KKTerm instances intentionally see the same installations. Removing or moving the portable folder neither stops nor uninstalls them. Portable mode keeps the detection cache in memory instead of writing the KKTerm detection-cache registry key.

**Liveness rule.** Install Helper work must not block KKTerm's UI thread. Catalog load, detection, cache reads, latest-version lookup, SQLite preference updates, install/uninstall, managed web UI launch/status/stop, and NSSM service registration/removal run on background workers or stream progress over `installer://progress`.

## Module layout

The page has a header and categorized sections:

- **Header.** Title (`installer.title`), subtitle (`installer.subtitle`), a page-level last checked status (`installer.lastChecked`) that switches to `installer.checkingForUpdates` while the background sweep runs, and two buttons:
  - `installer.refresh` — re-runs detection for every catalog tool, then queries the latest available version for every catalog tool whose provider can report one and caches the result.
  - `installer.updateAll` — installs every available update sequentially. Tutorial target: `installer.updateAll`.
- **Essentials** (`installer.section.essentials`) — recommended Windows setup patterns for Node, Python, and Git. The visible Node entry (`Node (nvm-windows)`) installs nvm-windows, then installs and activates the latest Node LTS release with nvm-windows. The visible Python entry (`Python (uv)`) installs uv, then installs the latest stable Python 3.13 patch release and pins Python 3.13 globally. Power users who want direct Node.js or CPython installer packages can install those outside Install Helper. winget itself lives in the **Package Managers** section, but all winget-backed catalog entries still declare `winget` as a prerequisite.

Grok Build offers WinGet (`xAI.GrokBuild`) and xAI's official PowerShell installer. Native-script uninstall removes only the installed command binaries and exact user-PATH entry, preserving Kimi/Grok credentials, configuration, sessions, logs, and other local data. Winget-installed command-line utilities add the winget links directory (`%LOCALAPPDATA%\Microsoft\WinGet\Links`) to the user PATH so new shells can find their commands.

Each tool surface is a **tile** in the section grid. The alternate list view keeps its Name, Installed, Latest, Status, and Action columns within a bounded readable width on wide displays instead of stretching the Name column across the full window. Both Gallery tiles and List rows expose the same base actions: installed tools with a known launch surface show `installer.actions.run`, while missing/outdated tools show `installer.actions.install` or `installer.actions.update`. Installed tools show an `installer.section.installed` badge. Tile version metadata is shown on separate `installer.tile.latest` and `installer.tile.installed` rows, rather than as provider kind text. Direct `download-installer` entries render `installer.status.web` as the latest value and link it to the download URL because those providers have no structured latest-version source. Windows feature, WSL distro, and multi-step bundle entries do not render `installer.tile.latest`. Runtime bundles add a third row: `installer.tile.node` for the Node runtime version, and `installer.tile.python` for the Python runtime version. Their `installer.tile.installed` row remains the manager version (nvm-windows or uv), so update checks compare like with like. While the startup or manual refresh sweep is running, version values show `installer.status.retrieving` and install/update actions are disabled. When `latestVersionSeen` has higher version precedence than `installedVersion`, the tool stays in its normal category section, the latest version value is highlighted, and the tile action uses `installer.actions.update`; equivalent trailing-zero build segments such as `26.01` and `26.01.00.0` are treated as equal. If a latest-version lookup for a supported provider errors, the tile's `installer.tile.latest` row shows that error instead of the generic unknown-version fallback. The page-level header status carries the most recent check time. One-step bundles usually inherit latest/detected version metadata from their child recipe; Node and Python bundles additionally show the detected runtime version once nvm-windows/uv and the managed runtime are present. Install/update actions open the app-owned popup dialog — `InstallerToolDialog` — that owns the detail surface (the previous inline expansion has been removed). Tutorial target on the options form inside the dialog: `installer.toolOptions`. New install dialogs preselect the provider from Settings → Install Helper → `settings.installerDefaultProvider` when the recipe offers both WinGet and Chocolatey. This preference is best effort: recipes that are only available from one provider still select that available provider, and users can still choose another exposed provider before starting the install.

Installed Gallery tiles and List rows with a known launch surface show `installer.actions.run`; its behavior depends on the tool's launch kind (`src/modules/installer/launch.ts`):

For command-line tools, the installed-details `installer.actions.run` action opens the same mini launcher dialog as the tile-level action. Coding-agent launchers show `installer.launcher.commandReference` as a system-browser link to the agent vendor's official command-line parameter documentation when one is available.

Spawned terminal launchers use normal interactive Windows PowerShell profile loading. After the profiles run, KKTerm preserves their environment and PATH ordering while appending any missing entries from the refreshed installer PATH. Editable command prefills use a one-shot `PowerShell.OnIdle` event instead of replacing the profile-defined `prompt` function.

- **GUI apps** (VS Code, Blender, Chrome, OBS Studio, …) start directly. The backend command `installer_launch_app` resolves a **closed per-tool allow-list** of executable candidates (`gui_launch_affordance`) in order — absolute `%VAR%`-token paths with optional `*` globs (highest match wins, e.g. versioned Blender directories), bare names against the refreshed PATH and the Windows `App Paths` registry, and `shell:AppsFolder` for MSIX/Store apps (ChatGPT Desktop) — then starts the first hit non-elevated with the executable's own directory as the working directory (OBS Studio requires this). No hit surfaces an error in the status bar.
- **Command-line tools** (Git, ripgrep, jq, fzf, winget, Chocolatey, Node and Python bundles, WSL, NSSM, Oh My Posh, Antigravity CLI, Claude Code CLI, Codex CLI, Cursor Agent CLI, Kimi Code CLI, Grok Build, OpenCode, Rustup, Bun, FFmpeg, scrcpy, psmux, Hermes AI Agent, OpenClaw) open a **mini launcher dialog** through `installer_open_terminal_launcher` with the tool on the refreshed PATH. General CLI tools show `installer.launcher.samples` command hints and use `installer.launcher.openTerminal` to open a normal PowerShell window with an editable command prefill. **Directory-scoped coding agents** (Antigravity CLI, Claude Code CLI, Codex CLI, Cursor Agent CLI, Kimi Code CLI, Grok Build, OpenCode) omit samples and instead show an `installer.launcher.commonOption` dropdown of current, tool-specific launch flags plus a free-text `installer.launcher.arguments` field above their recent folders. The selected preset and arguments persist per agent in the SQLite-backed durable UI-state key `kkterm.installerLauncherOptions.v1` and are executed immediately with the selected coding-agent CLI when the user runs it. Their launcher also remembers project folders: an `installer.launcher.recentFolders` list shows the five most recent folders (an `installer.launcher.showMore` inline action expands to all remembered ones, capped at twenty), clicking a folder runs the CLI there, and an `installer.launcher.chooseFolder` footer button opens the system folder picker and runs it in that folder. Opened folders move to the front of the list. The backend validates the requested folder (absolute path that still exists) before spawning. The remembered folders live in the durable UI-state store (`kkterm.installerLauncherRecentPaths.v1` — localStorage cache with SQLite write-through), so they survive reinstalls and are wiped by Settings → Reset All Settings.
- **Managed web apps** (n8n, Ollama, Flowise, Open WebUI, Langflow, Excalidraw, BentoPDF, OpenFlowKit) open a dedicated Run dialog with runtime status, `installer.actions.start` / `installer.actions.stop`, `installer.actions.openWebUi`, and service registration or removal. If a Windows service is registered but stopped, Start restarts that service instead of spawning a competing normal process. The n8n and Flowise Run dialogs also show `installer.dialog.nodeVersionSummary`: the current nvm Node version, the concrete launch runtime, and the package's required engine range. Before either app starts, KKTerm selects the newest compatible installed LTS under nvm-windows and repairs the service to use that concrete `node.exe` plus the package's declared executable. This avoids a later global nvm version switch breaking an existing service through the shared npm command shim. If Start fails, the Status Bar error uses `installer.status.nodeStartFailed` to preserve those version details alongside the helper error.
- **Tool suites** (Sysinternals Suite, Coreutils for Windows) open a dedicated searchable Run dialog. Their installation details never contain launcher controls.

The dialog has four rendering modes:

- **Installed info** — version, install location (when known), detected management-provider summary, detected winget install mode (`installer.options.scopeUser` or `installer.options.scopeMachine`, when known), and, for providers with a structured latest-version source, latest version + an inline `installer.refresh` action that checks only this recipe, last checked timestamp, pin-version switch, and an Update banner when `latestVersionSeen` compares newer than `installedVersion`. Direct download entries show `installer.status.web` as a link in the latest-version row instead. Runtime status, Web UI endpoints, terminal hints, suite launchers, and Windows-service controls are deliberately absent from installation details and live in the appropriate Run dialog. Footer: `Uninstall` (danger, omitted when no safe uninstall provider owns the detected copy) · `Run` for every installed tool with a known launch surface · `Update` (when available, including receipt-backed `uv self update`) · `Close`.
- **Not-installed info** — official website (`recipe.homepage`), release notes (`recipe.releaseNotesUrl`, with a provider-derived fallback for github/npm/winget when absent), latest version for providers with a structured latest-version source plus the same per-recipe inline `installer.refresh` action, `installer.status.web` latest-version links for direct download entries, provider summary, selected winget install mode, prerequisites list with installed/missing badges, and the options form. Footer: `Install` (primary) · `Cancel`.
- **Launcher** — opened from `installer.actions.run` in either base view or installed Details. GUI apps skip this mode and start directly. Managed web apps use a specialized Run dialog showing the reported endpoint, runtime status, and Windows service state; its footer owns Start/Stop, Open web UI, and Register/Remove service. CLI tools use the standard Run dialog: general tools show `installer.launcher.samples`, while coding agents show `installer.launcher.commonOption`, `installer.launcher.arguments`, command-reference links, and recent folders. Tool suites use the specialized searchable Run dialog: `installer.quickLaunch.search` filters rows by name/executable/description; GUI entries expose `installer.quickLaunch.launch`, CLI entries show `installer.quickLaunch.cli`, and the footer opens either elevated Sysinternals PowerShell (`installer.quickLaunch.openTerminal`) or a normal Coreutils terminal (`installer.launcher.openTerminal`). Footer for the standard dialog: `installer.launcher.chooseFolder` (coding agents only) · `installer.launcher.openTerminal`/`installer.actions.run` (primary) · `Close`.
- **Stepper** — opened when the user presses Install/Update, or when reopening the dialog while an install/uninstall is in flight or has just terminated. The body renders the n8n-style step list with status dots (`pending`/`running`/`done`/`failed`), per-step duration / active-step ratio, and a click-to-expand per-step log panel. Winget progress is best-effort: KKTerm shows determinate progress when winget emits carriage-return percentage or downloaded/total frames, and falls back to elapsed-time heartbeats when the underlying installer is silent. Terminal states swap the dialog title (`installer.dialog.installedTitle` / `installer.dialog.failedTitle` / `installer.dialog.cancelledTitle`). Failed installs leave the stepper dialog open on the failed package, including prerequisite packages and Update all entries, so the user can read or copy the streamed stdout/stderr logs instead of being bounced back to an info-style dialog. The failure message also includes the most useful recent child-process output line when one is available, so package-manager causes are visible without expanding the full log.

## Tool detection

Detection renders in two phases on Module entry. First, KKTerm loads the local Windows Registry detection cache from `HKCU\Software\Ryan Tsai\KKTerm\InstallerDetectionCache` on a worker and paints any remembered states immediately. Then the backend starts a bounded streaming revalidation sweep in the background without blocking the Module. Each completed tool emits a `detectResult` event over `installer://progress`, updates the tile, and writes the fresh state back to the registry cache. After detection finishes, KKTerm runs an interval-gated latest-version check: it queries latest versions for every catalog tool whose provider can report one only when the configured interval has elapsed since the last completed check attempt (see Update flow). `installer.refresh` re-runs the same detection and forces a latest-version check on demand regardless of the interval.

Per-provider detection methods:

- **winget** — detection reads a local Add/Remove Programs registry snapshot once per fresh detection sweep and matches catalog aliases (`registryKeys`, `displayNames`, `displayNamePrefixes`) so existing installs can be recognized even when winget would report an `ARP\...` identifier. Store/MSIX apps without an ARP entry can declare exact `appxPackageFamilyNames`; KKTerm enumerates the current user's packages once in the same snapshot and reads their installed package version. The snapshot is cached in memory until the next explicit detection call. Fresh results are persisted to the Install Helper registry cache. Selected winget recipes also have narrow fallbacks when the registry snapshot misses them: `oh-my-posh version`, `pwsh --version`, and receipt-backed Astral standalone uv detection. Standalone uv recognition first reads Astral's install receipt (`%XDG_CONFIG_HOME%\uv\uv-receipt.json` when that override is configured, otherwise `%LOCALAPPDATA%\uv\uv-receipt.json`, matching `install.ps1`) and checks the install prefix it records, then falls back to current and persisted PATH entries, `UV_INSTALL_DIR`, the current `%USERPROFILE%\.local\bin` default, and the legacy `.cargo\bin` location. A candidate directory is only accepted when it matches the config receipt's install prefix; the receipt requirement distinguishes Astral's installer from pipx, Scoop, Cargo, or another `uv` that merely appears on PATH. A recognized standalone copy is marked with the `officialScript` install source: the UI labels it with `installer.status.installedOfficialScript` / `installer.dialog.providerOfficialScript`, propagates that source to the Python bundle, checks `astral-sh/uv` releases for updates, and runs the exact receipt-backed executable with `uv self update`; it participates in Update and Update all without ever routing through WinGet. Uninstall remains omitted because the receipt does not authorize removing a possibly separate WinGet package. Latest-version checks for ordinary WinGet installs prefer the structured Microsoft `winget-pkgs` manifest repository so they do not depend on localized `winget show` labels; KKTerm only treats version-shaped manifest directories as latest-version candidates and ignores sibling channel folders such as prerelease or alternate-edition branches. When that lookup is unavailable, KKTerm falls back to `winget show`, accepts winget source agreements for first-run Windows machines, and uses `CREATE_NO_WINDOW` so no `cmd.exe` window flashes on Module entry.
- **Chocolatey** — curated winget rows may expose Chocolatey in `installer.options.provider` when the package id was verified in the Chocolatey community feed. Selecting Chocolatey requires the `chocolatey` recipe; if it is missing, KKTerm opens that recipe's install dialog first. Detection uses local `choco list --local-only --exact --limit-output`. Once a row is detected as installed through Chocolatey, KKTerm uses `choco search --exact --limit-output` for latest-version checks, `choco upgrade` for updates, and `choco uninstall` for uninstall. Every Chocolatey **install, update, and uninstall runs elevated** — Chocolatey writes to `C:\ProgramData\chocolatey` and always requires Administrator, so each op raises exactly one UAC prompt via `Start-Process -Verb RunAs` (KKTerm itself stays non-elevated) and applies machine-wide for all users. Because an elevated child cannot share pipes across the UAC boundary, the elevated command redirects its output to a temp log that KKTerm tails into the stepper. The dialog states the requirement up front via `installer.dialog.adminRequiredChocolatey`, and the update and uninstall confirmations carry an `installer.confirm.adminChocolateyFooter` notice. Declining the UAC prompt fails the op cleanly (Windows `ERROR_CANCELLED` / 1223).
- **npm** — `npm ls -g --json --depth=0`. Looks up the package in the top-level `dependencies`. Managed npm apps such as n8n, Flowise, and OpenClaw use an app-local marker instead.
- **uv pip** — app-local Python virtual environments created with uv. Open WebUI, Langflow, and Hermes AI Agent use this provider and are detected by their app-local marker after KKTerm installs them.
- **download-installer** — downloads a vendor-declared installer URL to a temp file and runs the downloaded installer. `.appx`, `.appxbundle`, `.msix`, and `.msixbundle` downloads are installed with PowerShell `Add-AppxPackage`; the winget/App Installer recipe also requests `Microsoft.DesktopAppInstaller_8wekyb3d8bbwe` family registration before and after installing the downloaded bundle so first-login Windows 11 images can register `winget.exe`. Other downloads launch with the normal Windows installer UI. ChatGPT Desktop (Codex) uses this path because OpenAI now manages the former Codex desktop app as the new ChatGPT desktop app with Chat, Work, and Codex; detection accepts both ChatGPT/legacy Codex Add/Remove Programs names and the current-user `OpenAI.Codex_2p2nqsd0c76g0` package family, including its installed package version. Hermes Desktop uses Nous Research's unversioned canonical `Hermes-Setup.exe` URL, which serves the current installer, and intentionally has installed-version detection only—there is no latest-version comparison. Some winget desktop-app recipes also expose this as an optional provider when a canonical vendor installer URL exists.
- **GitHub-release download provider** — selected winget recipes can offer a direct GitHub release fallback when the vendor publishes portable archives instead of a conventional installer. Zip fallbacks extract under `%LOCALAPPDATA%\KKTerm\installer\bin\<tool_id>\`; catalog metadata can point Add to PATH at a nested executable directory inside the archive. Once KKTerm detects the marker for one of these managed fallback installs, latest-version checks and updates keep using the GitHub-release provider instead of switching back to winget.
- **github-release / managed app** — a marker file under `%LOCALAPPDATA%\KKTerm\installer\bin\<tool_id>\` or `%LOCALAPPDATA%\KKTerm\installer\apps\<tool_id>\` written at install time. Only installs we performed count as "managed".
- **windows-feature** — `dism /online /get-featureinfo /featurename:<X>`. Parses the `State :` line.
- **wsl-distro** — `wsl --list --quiet`. Matches the distro name declared in the catalog.
- **bundle** — installed iff every step's detection is installed; otherwise the row shows `installer.status.partial` with an `installed/total` count. One-step bundles inherit the child version. Installing or updating a bundle skips already-current installed steps, but re-runs an installed step when that step's latest-version check reports a newer manager version.

Runtime command probes such as `node --version`, `uv python find 3.13`, global npm package detection, managed app version probes, and managed web UI launchers use or retry with the refreshed persisted Windows PATH when the current KKTerm process cannot resolve the command. This lets a fresh nvm-windows, uv, or npm install re-detect and launch related npm-backed tools correctly without requiring a KKTerm restart.

Installed GUI launchers do not assume that the executable is on `PATH`. The backend resolves current-user AppX package-family registrations and manifest application IDs, Start-menu AppIDs from `Get-StartApps`, matching Add/Remove Programs `DisplayIcon` executables, and Windows App Paths before trying the catalog's known install-location fallbacks. Start-menu matches prefer exact names over prefixes and reject help pages, URLs, and executables outside the tool's closed automatic executable allow-list; duplicate uninstall registrations prefer the highest displayed version. Icon-only or unrelated `DisplayIcon` targets are ignored, so tools such as VcXsrv continue to open their intended interactive launcher instead of a background executable. This supports per-user, per-machine, Store/MSIX, and alternate vendor layouts.

If every automatic GUI resolver fails, the Run action opens a native file picker titled with `installer.launcher.selectAppTitle`. The picker accepts Windows `.exe`, `.com`, `.bat`, `.cmd`, and `.lnk` files. The backend verifies that the chosen path is absolute, exists, is a file, and has one of those extensions before launching it. A successful choice is remembered per tool in the SQLite-backed durable UI-state key `kkterm.installerGuiLauncherPaths.v1` and is retried only after the automatic resolvers on later launches. Missing or invalid remembered files are discarded and the picker is offered again.

## Install flow

1. The user clicks `installer.actions.install` on a row.
2. The frontend resolves the install plan: transitive `needs` are walked, and prerequisites already detected as installed are skipped. If a winget-backed recipe is installed with `installer.options.provider` set to direct download, the winget prerequisite is skipped for that install because the selected provider does not call `winget.exe`.
3. If the plan has unresolved prerequisites OR a non-zero UAC-prompt estimate, a confirm dialog (`installer.confirm.installTitle`) lists the prerequisites and a footer (`installer.confirm.uacFooter`) names the estimated prompt count.
4. On confirm, the backend dispatches the install in a worker thread. The dialog flips to stepper mode for the package currently being installed, including prerequisites. Every operation immediately receives the shared three-card progress template: dependency preparation, the named install/uninstall action, and verification. This is the default presentation for every current recipe and for future catalog additions; providers do not need custom progress UI code. Progress streams to the frontend on the `installer://progress` Tauri event channel as a discriminated union: `plan` (an optional provider-specific step list that replaces the default template), `stepStarted` / `stepFinished` (per-step lifecycle), `stdout` / `stderr` / `progress` (each carrying an optional `stepId` so the UI can route lines and ratios to the active step row), `step` (free-form provider activity that advances the default action stage), `completed`, `failed`, `cancelled`. A `failed` or `cancelled` event stops the queue and keeps the dialog in stepper mode on that package with its streamed logs visible.
   The progress header shows the active command beneath the package name and wraps long commands or filesystem paths within the dialog instead of clipping them at the right edge.
   Managed npm applications such as n8n replace the default with the more specific three-stage plan `installer.steps.resolveDependencyPlan`, `installer.steps.ensureNodeLts`, and `installer.steps.installNamed`. The Node stage installs and activates the current LTS with nvm-windows rather than accepting any installed Node release. The active stage owns its command output and always shows a progress track; when a provider does not report a defensible percentage, the track remains indeterminate instead of inventing one.
   Runtime bundle follow-up commands and npm package installs refresh PATH plus relevant persisted Windows user and machine environment variables before spawning. This lets freshly installed managers such as nvm-windows and uv run their immediate `nvm install lts`, `uv python install ...`, or npm-based AI-agent install steps without restarting KKTerm or Windows. The refreshed child environment also includes existing Git for Windows command directories so later child installers can resolve `git` in the same KKTerm session. The uv recipe is a WinGet portable package; before updating it, KKTerm checks for running `uv.exe` processes and asks the user to close uv-based tools when they would block replacing the portable executable. The base WSL recipe runs `wsl --install --no-distribution`, so Docker can depend on WSL without silently installing Ubuntu or launching Linux first-run setup. WSL distribution shortcuts are separate recipes that run `wsl --install --distribution <name> --no-launch`; if base WSL was installed as their prerequisite in the same queue, the queue stops at the reboot boundary and the distro install is retried after restart.
   Claude Code CLI uses Anthropic's `Anthropic.ClaudeCode` WinGet package as its default provider, with the global `@anthropic-ai/claude-code` npm package available from `installer.options.provider`. The default install plan requires WinGet; selecting npm replaces that prerequisite with the Node bundle. KKTerm also adds the WinGet portable-links directory to the user PATH after a WinGet installation so `claude` is available to the Settings AI setup flow without an app restart. Existing npm installations are detected and remain npm-managed for updates and uninstall.
5. After a `completed` event, the row re-runs detection automatically and moves to the Installed section.

## Update flow

1. KKTerm evaluates the update sweep each time the user switches to the Install Helper Module from another Module. The automatic sweep runs only when the configured check interval (Settings → Install Helper → `settings.installerCheckInterval`; one of hour / day / week / month, default daily) has elapsed since the last completed check attempt; otherwise the persisted check state is reused without a network fetch. The user can also force a check by clicking `installer.refresh` in the header for every supported recipe or beside the latest version inside one recipe's detail dialog.
2. The backend launches a **streaming** worker and returns after the worker starts. It emits `checkStarted` with the id list, then per-tool `checkResult` events as each lookup lands (latest-version queries run in parallel — `winget show`, npm registry, PyPI, GitHub releases API — bounded to a small pool to hide slow legs behind fast ones), and finally `checkFinished`. For WinGet recipes, the configured WinGet source is authoritative because it is the source the update command can install from; the Microsoft `winget-pkgs` repository is used only when `winget show` is unavailable. The frontend only sends recipes whose providers can report a structured latest version. It writes each completed result into `toolState` as it arrives so rows light up incrementally instead of after one large blocking await. Per-tool lookup errors stay in frontend session state and render in the `installer.tile.latest` / `installer.dialog.latestVersion` row; they update the durable check time without overwriting the persisted latest-version cache. Results and attempt times are persisted in the `installer_tool_state` SQLite table.
3. Rows whose `latestVersionSeen` compares newer than `installedVersion` stay in their normal category section, highlight the latest version value, and show their per-row `installer.actions.update` button.
4. Clicking `installer.updateAll` lists every pending update in a dialog (`installer.confirm.updateAllTitle`), warns about the likely UAC prompt count, and on confirm runs the queue sequentially. Pinned tools (see Pin version below) are skipped.

If WinGet reports that an `upgrade` has no applicable newer package, KKTerm treats the result as a nonfatal no-op instead of a failed install. If local registry detection found the tool but `winget upgrade` cannot match it as an installed package — common when the tool was originally installed from the vendor's official Windows installer instead of by WinGet — KKTerm retries the same package id with `winget install` so WinGet can run the current installer over the existing app. After every completed install or update, KKTerm immediately refreshes that tool's latest version from its selected provider so stale update availability does not remain visible. Other non-zero WinGet results still fail the operation and surface their diagnostic output.

The automatic sweep is triggered only by switching to the Install Helper Module, and at most once per configured interval; there is no background timer polling while the Module is inactive. The last-check timestamp is persisted per tool in `installer_tool_state` (`last_check_at`) so the interval is honored across app launches.

## Uninstall flow

1. The user clicks `installer.actions.uninstall` on an installed row.
2. The frontend runs a reverse-dependency check: every catalog recipe whose `needs` includes this row's id AND whose detection says installed is collected.
3. If dependents exist, the confirm dialog (`installer.confirm.uninstallTitle`) lists them with the warning `installer.confirm.uninstallDependentsBody` and the footer `installer.confirm.uninstallDependentsFooter`. Otherwise the dialog shows the simple body `installer.confirm.uninstallSimpleBody`.
4. On confirm, the backend dispatches per-provider uninstall: `winget uninstall`, `npm uninstall -g`, `uv pip uninstall`, `Remove-Item -Recurse` on the github-release or managed-app install directory, `dism /online /disable-feature`, or `wsl --unregister <distro>` for WSL distro shortcuts. Download-installer desktop apps that do not expose a safe structured uninstall path tell the user to uninstall from Windows Settings.

There is intentionally no "Uninstall all" action.

## Cancellation

Per row, an in-flight install/uninstall surfaces an `installer.actions.cancel` button. Cancel raises an `AtomicBool` flag the worker thread polls; on the next check it kills the child process and emits `cancelled`. Partial installs are **not rolled back** — the underlying installer's transactionality is what it is.

For "Update all", cancel stops the **queue** (the next-up tools), not the in-flight install.

## Options

Each recipe declares a subset of these options (the set is closed):

- **`installer.options.provider`** — winget (default) vs direct download, Chocolatey, or npm provider. Shown only for recipes whose catalog entry declares a canonical `downloadProvider`, verified `chocolateyProvider`, or supported `npmProvider`. Choosing download hides winget-only options, removes the winget prerequisite for that install, and shows download-provider options such as GitHub-release location/Add to PATH when applicable. Choosing Chocolatey replaces winget with the `chocolatey` recipe as the package-manager prerequisite and then manages that row with `choco`. Choosing npm replaces winget with the Node bundle and manages that row as a global npm package.
- **`installer.options.scope`** — `user` (default, `installer.options.scopeUser`) vs `machine` (`installer.options.scopeMachine`). Winget recipes only. KKTerm passes `--scope user` by default for scoped winget recipes, including prerequisite installs inside bundles. User Mode means KKTerm asks winget for a current-user install; it is no-UAC only when the package's own installer supports a non-elevating user install. Known self-elevating user-mode installers show `installer.options.scopeSelfElevatingHint`; for those recipes, and for known machine-only winget recipes such as Docker Desktop, KKTerm launches the winget operation through the elevated helper so the user gets the expected UAC prompt even when KKTerm itself is not running as administrator. System Mode(UAC) always triggers UAC.
- **`installer.options.version`** — specific version string, or empty = `installer.options.versionLatest`.
- **`installer.options.location`** — install location override. Winget: `--location`. github-release: extraction directory.
- **`installer.options.addToPath`** — github-release recipes only. Appends the cataloged executable directory (or the install directory when no nested path is declared) to user PATH via PowerShell after extraction.
- **`installer.options.pinVersion`** — row-level switch. When enabled, this tool is **excluded** from `installer.updateAll`. Pinning does not prevent a per-row update click.

## WSL distro manager

Once base WSL is installed, its installed-tool dialog exposes an `installer.wsl.manageDistros` action that opens the WSL distro manager. Unlike the static `wslDistro` catalog shortcuts, the manager reflects live host state derived from `wsl.exe` rather than the catalog, so it sees every distribution — including ones installed outside KKTerm:

- **List** — `wsl --list --verbose` (decoded from UTF-16LE) yields each distro's name, default marker, WSL version, and running state. The parser keys off the `*` default marker and the trailing version digit instead of the localized column headers.
- **Set default** — `wsl --set-default <distro>` retargets bare `wsl`/`wsl --install`.
- **Unregister** — `wsl --unregister <distro>` permanently deletes the distro and all of its files; the manager requires a danger-tone confirmation first.
- **Install** — the install picker is populated from `wsl --list --online` (installed distros filtered out) and installs the selected one with `wsl --install --distribution <distro> --no-launch`.

Distro names passed to the state-changing commands are validated to be plain identifiers (alphanumerics plus `-`, `_`, `.`, no leading dash) so a name can never smuggle extra `wsl` arguments. The backend commands (`installer_wsl_list_distros`, `installer_wsl_list_online`, `installer_wsl_set_default`, `installer_wsl_unregister`, `installer_wsl_install`) run the blocking `wsl.exe` calls off the UI thread.

## WSL reboot gating

When the user installs base WSL in the current app session, the Install Helper sets a session-only flag `wslJustEnabled`. While that flag is set, any recipe that transitively `needs` WSL (Docker Desktop and WSL distro shortcuts in the v1 catalog) shows the hint `installer.wslReboot` and its install button is disabled. The flag resets only when KKTerm is restarted — which is what happens during a real Windows reboot.

## Persistence

- **SQLite** — table `installer_tool_state(tool_id PK, pinned, latest_version_seen, last_check_at)` (added in schema migration 17). Pinning and the cached latest available version survive restarts.
- **Windows Registry** — per-tool detection cache under `HKCU\Software\Ryan Tsai\KKTerm\InstallerDetectionCache`. This cache is local Windows state, not portable settings data.
- **Debug log** — debug builds write Install Helper catalog, detection, latest-version, install, uninstall, cache, progress-event, and child-process output records to `installer.helper.debug.log` beside `kkterm.log`. Release builds write the same JSONL log only when `settings.advancedDebugging` is enabled. The same setting also enables `kkterm-heartbeat.debug.log` in release builds for frontend/native liveness timing while troubleshooting Install Helper stalls.
- **In-memory only** — the active detection sweep, the in-flight install queue, the WSL reboot flag, and the per-tool log buffer.
- **On-disk install dirs** — `%LOCALAPPDATA%\KKTerm\installer\bin\<tool_id>\` holds installed `githubRelease`-provider tools, including winget recipes installed through a GitHub-release `downloadProvider`, and their `.kkterm-installer.json` marker file. `%LOCALAPPDATA%\KKTerm\installer\apps\<tool_id>\` holds managed server apps such as n8n and Ollama, plus their app-local marker and data folders. These are installed-tool state, not catalog cache.

## Catalog source

The catalog `installer/catalog.v1.json` is **embedded into the KKTerm binary at compile time** via `include_str!`. Updates to the catalog ship with the next KKTerm release — there is no network fetch, no on-disk cache, and no signature verification. The trust anchor is the app binary itself (eventually backed by Windows code-signing of the KKTerm installer).

Adding, editing, or removing a tool is a normal commit to `installer/catalog.v1.json` followed by a release. The `shipped_catalog_parses_and_validates` test embeds the same JSON via `include_str!` and runs `Catalog::validate()`, so malformed edits fail `cargo test` before they can ship.

See [`docs/ADR/0008-installer-helper-bundled-catalog.md`](../ADR/0008-installer-helper-bundled-catalog.md) for the design rationale and what it supersedes from [ADR 0007](../ADR/0007-installer-helper-remote-catalog.md).

## Limits

- AI Assistant integration is deferred. The AI does **not** have a Tauri command to trigger installs in v1.
- "Latest version" detection for multi-step `bundle`, `windowsFeature`, and `wslDistro` recipes returns null — the rows do not surface update suggestions. One-step bundles inherit latest-version checks from their child recipe.
- The UAC prompt count shown in confirm dialogs is a best-effort estimate; some installers (including Git for Windows, nvm-windows, Docker Desktop, and system MSIs) self-escalate even when `--scope user` is passed.
